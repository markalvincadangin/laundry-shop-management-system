## Research Summary (Research Harness)
Generated by /speckit-harness-report on 2026-07-13. State: specs/008-system-integrity-review/harness/

### Verdict
Research across two sessions (2026-07-08 and 2026-07-13) confirmed that the system's core architecture is sound but initially had critical client pain points unaddressed. The #1 client stressor — machine malfunctions and downtime — was confirmed missing (E001) and subsequently addressed by the full machine management module implemented in spec-008. The second client concern, rush order mixing (E003), was initially flagged but refuted (V004): `OrderPipeline.tsx` already sorted and badged rush orders; this was then formalized and strengthened in spec-009 (Rush Fee Refactor) which replaced the string-based detection with a native `isRush` boolean flag, automatic Rush Fee injection, and queue ordering by `isRush DESC, createdAt ASC`.

For **Mission 2** (Data Integrity), the schema and JPA layer are clean: FK constraints and cascade behaviors match intentional design (E006, V008), and module isolation is strictly respected with zero undocumented cross-domain coupling (E007, V009). Minor cosmetic naming divergences exist between the DBML ERD and the implemented DB schema (E005, E008) but carry no functional risk.

For **Mission 3** (new feature verification), the `isRush` flag, `add_on_catalog` table, queue priority sorting, RUSH badge UI, and Admin add-on management page were all implemented and verified via the spec-009 lifecycle (specify → plan → tasks → implement → review). The `AuditLogPerformanceTest` shows a 40% degradation under test conditions (threshold: 30%), which warrants monitoring but is likely an artifact of the test environment, not production.

Budget spent: 17 searches, 7 inspections, 12 verifications across 18 actions. Stop reason: mission answered and all critical claims verified.

### Key Findings (curated set)
- **E009 (critical — Fixed)**: `OrderService` bypassed BR-MAC-03 with a hardcoded 10-machine limit instead of reading from configuration. Fixed in Phase 5 alignment; now reads from `MachineRepository.count()` against the spec limit.
- **E001 (critical — Fixed)**: Machine entities, tracking, and downtime were completely absent despite being the #1 client pain point. Full machine management module implemented in spec-008.
- **E010 (high — Fixed)**: Core docs (business-rules.md, user-stories.md, erd.dbml) were missing all machine management feature entries. All three documents updated in Phase 5 alignment.
- **E006 (high — Verified)**: Foreign keys and `ON DELETE CASCADE` exactly match the intentional ERD design; no unintended Hibernate JPA cascades exist. (V008)
- **E007 (high — Verified)**: JPA mappings respect constitution module boundaries. `customers`, `users`, and `rates` do not import `orders`. (V009)
- **E004 (medium — Open)**: Admin-requested comparative analytics (monthly/yearly comparison) still absent. Deferred to a future spec.
- **E002 (medium — Design Decision)**: Power interruptions are out of scope for v1 without IoT hardware. A shop-wide "System Pause" flag was designed in brainstorm (2026-07-09) as the pragmatic alternative; implementation is tracked separately.
- **E003 (refuted via V004 → resolved in spec-009)**: Rush order mixing was already partially addressed by UI sorting; fully resolved by the spec-009 Rush Fee Refactor which introduces `isRush` as a first-class DB column.
- **E005 / E008 (low — Cosmetic only)**: ERD uses `notifications` and `activity_logs`; implemented DB uses `client_alerts` and `audit_logs`. No functional impact.

### Corrected Assumptions
- **Rush orders lack UI flow (E003)**: Refuted by V004. `OrderPipeline.tsx` and `OrderCard.tsx` already sorted and badged Rush Orders. Assumption removed; further strengthened in spec-009.
- **Auth missing on Customer/Order endpoints (V001 candidate)**: Refuted. `CustomerController` and `OrderController` have proper `@PreAuthorize` guards; the initial grep did not find explicit annotations because they inherit from a security config layer.

### Open Questions
- **Comparative Analytics (E004)**: Admin interview requested monthly/yearly performance comparison. Not implemented; schedule for a future spec phase.
- **System Pause UI (E002)**: The shop-wide pause feature was designed in the spec-008 brainstorm session but not yet implemented. Should this be added to the spec-008 tasks backlog or promoted to a standalone spec-010?
- **AuditLogPerformanceTest degradation**: Test shows 40% write degradation vs 30% threshold. Needs profiling in a controlled environment to confirm whether this is a test-harness artifact or a genuine production concern.
